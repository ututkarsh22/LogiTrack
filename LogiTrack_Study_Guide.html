🔢 Recommended Study Sequence

Read files in this exact order. Each layer builds on the previous one.

Phase 1: Backend Foundation

Goal: Understand how data is shaped and stored.

Step 1 — Environment & Database Config

# File What to Focus On
1 .env What env variables exist (PORT, MONGO_URI, JWT_SECRET, CORS_ORIGIN)
2 config/db.js How MongoDB connects via Mongoose
3 config/dotenv.js dotenv setup

Step 2 — Mongoose Models (Data Shapes)

# File What to Focus On
4 User.js name, email, password, role (customer/agent) — the base identity
5 Agent.model.js Extends User via ref: "User". Has location {lat,lng}, isAvailable, orderId
6 Order.js The core order with pickup/drop coords, addresses, OTPs (select:false), fare, status enum
7 OrderHistory.js Mirror of Order — data moves here after delivery. Has deliveredAt timestamp
💡 Key Pattern Agent is a separate document linked to User via ObjectId, not a field on User. This 1:1 relationship lets agents have location/availability without polluting the User model.

Step 3 — Utilities (Pure Logic)

# File What to Focus On
8 getCoordinates.js Calls Nominatim (OpenStreetMap) to convert address string → {lat, lng}
9 distance.js Haversine formula — calculates distance between 2 lat/lng points in km
📝 Note These two utils are the backbone. Every order creation geocodes addresses and every fare calculation uses Haversine distance.

Phase 2: Backend Security & Routing

Goal: Understand request flow from HTTP → controller.

Step 4 — Middleware (The Gatekeeper)

# File What to Focus On
10 auth.middleware.js Three functions: verifyToken (JWT from cookie), requireRole (role-based access), verifyAdmin
⚠️ Key Concept Every protected route goes through verifyToken → requireRole('customer'|'agent'). The JWT is stored in an httpOnly cookie, not localStorage. This is more secure against XSS.

Step 5 — Routes (URL → Controller Mapping)

# File What to Focus On
11 authRoutes.js POST /register, POST /login, POST /logout, GET /verify
12 orderRoute.js All customer-only: GET /all-orders, POST /take-order, POST /calculate-fare, GET /history
13 agentRoutes.js All agent-only: POST /location, GET /status, POST /verify-pickup-otp, POST /verify-delivery-otp

Phase 3: Backend Controllers (Business Logic)

Goal: Understand what happens when each API is called.

Step 6 — Auth Controller

# File What to Focus On
14 authControllers.js registerUser — hashes password, creates User + Agent doc if role=agent. loginUser — compares password, signs JWT, sets cookie. verifyAuth — validates session.

Step 7 — Order Controller ⭐ MOST IMPORTANT

# File What to Focus On
15 orderController.js Study createOrder carefully — it geocodes → calculates fare → generates OTPs → creates order → tries to auto-assign nearest agent within 10km. Also calculateFare for the estimate feature.
⚠️ Atomic Assignment Pattern When creating an order, the code uses findOneAndUpdate with { status: "pending" } condition. This prevents two agents from being assigned the same order simultaneously (race condition protection).

Step 8 — Agent Controller ⭐ KEY FILE

# File What to Focus On
16 agentControllers.js agentLocation — updates location AND tries to find pending orders within 10km. verifyPickupOtp — changes status assigned→picked. verifyDeliveryOtp — moves order to OrderHistory, frees the agent.
💡 Order Lifecycle pending → assigned → picked → in-transit → delivered (moved to OrderHistory).
The picked → in-transit transition happens via a polling job in server.js, not via an API call.

Phase 4: Server Entry Point

# File What to Focus On
17 server.js Ties everything together: CORS config, cookie parser, 3 rate limiters (auth:20, orders:30, agent:40 per 15min), route mounting, and the polling job that auto-transitions orders from picked → in-transit after 5 minutes.

Phase 5: Frontend Foundation

Goal: Understand how the React app is structured and how auth works.

Step 9 — App Shell

# File What to Focus On
18 main.jsx React entry point
19 api/axios.js Axios instance with baseURL, withCredentials:true (sends cookies), 401 interceptor auto-redirects to login
20 ThemeContext.jsx Dark/light mode toggle via localStorage
21 AuthContext.jsx login(), logout(), session verification on mount, useAuth() hook
22 App.jsx Study the ProtectedRoute component — wraps routes with role checks. Routing structure: /customer/* and /agent/*

Step 10 — Shared Components

# File What to Focus On
23 Navbar.jsx Conditional nav links based on role, logout button, theme toggle

Phase 6: Frontend Pages

Goal: Understand each page's UI and how it talks to the backend.

# File What to Focus On
24 Landing.jsx Marketing page, no API calls
25 Register.jsx Form → POST /auth/register → redirect to login
26 Login.jsx Form → POST /auth/login → AuthContext.login() → redirect by role
27 CustomerDashboard.jsx ⭐ MOST COMPLEX PAGE. Order form, fare calculator, Leaflet map with OSRM route, order list with OTP display. Study MapController, RouteLayer components and handleCreateOrder.
28 OrderHistory.jsx Grid/list view toggle, expandable order cards
29 AgentDashboard.jsx ⭐ Two views: assigned order (map + sidebar with OTP forms) vs idle (location sync + scanning radar). Study updateLocation and OTP verification flows.

🔄 Data Flow Walkthroughs

Flow 1: Customer Places an Order

sequenceDiagram participant C as Customer Browser participant F as Frontend participant B as Backend API participant N as Nominatim participant DB as MongoDB C->>F: Fills pickup, drop, category - clicks BOOK NOW F->>B: POST /orders/take-order B->>N: getCoordinates pickupLocation N-->>B: lat, lng B->>N: getCoordinates dropLocation N-->>B: lat, lng B->>B: getDistance - fare = round distance x 10 B->>B: Generate pickupOtp + deliverOtp B->>DB: Orders.create status pending B->>DB: AgentModel.find isAvailable true B->>B: Find nearest agent within 10km alt Agent found B->>DB: Order.findOneAndUpdate status assigned B->>DB: Agent.isAvailable = false end B-->>F: success, order F->>F: setSelectedOrder - Map shows route F->>F: fetchOrders - Refresh list

Flow 2: Agent Delivers the Order

sequenceDiagram participant A as Agent Browser participant F as Frontend participant B as Backend API participant DB as MongoDB A->>F: Syncs location GPS or text F->>B: POST /agent/location B->>DB: Agent.location = coords B->>DB: Find pending orders within 10km alt Order found B->>DB: Atomic assign pending to assigned B-->>F: assignedOrder F->>F: Show map with pickup to drop route end Note over A,DB: At Pickup Point A->>F: Enters 4-digit pickup OTP F->>B: POST /agent/verify-pickup-otp B->>DB: Verify OTP - status picked B-->>F: success, order Note over B,DB: After 5 minutes server polling job B->>DB: status picked to in-transit Note over A,DB: At Drop Point A->>F: Enters 4-digit delivery OTP F->>B: POST /agent/verify-delivery-otp B->>DB: Create OrderHistory record with fare B->>DB: Delete from Orders collection B->>DB: Agent.isAvailable = true, orderId = null B-->>F: success

🧠 Key Concepts to Understand

Concept Where It's Used Why It Matters
JWT in httpOnly Cookie auth.middleware.js, authControllers.js More secure than localStorage — immune to XSS
Role-Based Access requireRole('customer'|'agent') in routes Customers can't access agent APIs and vice versa
Haversine Formula distance.js Calculates "as the crow flies" distance between GPS coords
Geocoding getCoordinates.js (Nominatim) Converts "Connaught Place, Delhi" → {lat: 28.63, lng: 77.21}
OSRM Routing Frontend RouteLayer component Fetches actual road route (not straight line) for map display
Atomic DB Updates findOneAndUpdate({status:"pending"}) Prevents race conditions in order assignment
OTP Dual Verification pickupOtp + deliverOtp Ensures physical presence at both pickup and drop points
Order Lifecycle Order → OrderHistory migration Active orders live in Orders collection, delivered ones move to OrderHistory
Rate Limiting server.js (express-rate-limit) Prevents API abuse: auth=20, orders=30, agent=40 per 15min
Polling Job server.js setInterval Auto-transitions picked → in-transit after 5 min
